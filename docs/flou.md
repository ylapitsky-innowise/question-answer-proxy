# Как это работает:

- Прокси-сервис — это Resource Server. Он не занимается выдачей токенов, а только проверяет их подпись и срок действия.
- Клиент (JAR) — при первом запуске (или при необходимости) запрашивает токен у прокси-сервиса, передавая логин/пароль. 
- Прокси-сервис проверяет учётные данные (например, из конфигурации или БД) и выдаёт подписанный JWT.
- Все последующие запросы к /api/v1/** клиент выполняет с заголовком Authorization: Bearer <JWT>.

## Модель данных:
Так, как набор и количество полей у различных списков отличается - то данные (списки) рассматриваем как двумерный массив (List<List<Object>>), а не как жёстко зафиксированный набор полей.

## Подход:
1. **Чтение заголовков:** При синхронизации сначала читайте первую строку листа — это заголовки. Строим `Map<String, Integer>`, где ключ — название колонки (например, `"question"`, `"answer"`, `"topic"`, `"difficulty"`), а значение — её индекс.
2. **Гибкий маппинг:** При обработке каждой строки данных используем эту карту, чтобы безопасно извлекать значения. Если колонки с каким-то атрибутом нет, поле в DTO просто останется `null`.
3. **Нормализованная модель:** Внутри приложения вы работаете с единым DTO `QuestionAnswer`, которое имеет все возможные поля (`id`, `question`, `answer`, `topic`, `difficulty`, `tags`, `notes` и т.д.). Это позволяет клиенту не зависеть от структуры конкретной таблицы.


Такой подход делает сервис устойчивым к изменениям в таблицах и позволяет легко добавлять новые атрибуты в будущем.


## Структура кода: слоистая архитектура (Layered Architecture):
```text
com.innowise.qaproxy
├── config/           # Конфигурация (Security, Jackson, Google Sheets)
├── controller/       # REST-контроллеры (принимают HTTP-запросы)
├── dto/              # Data Transfer Objects (модели для API)
├── exception/        # Кастомные исключения и GlobalExceptionHandler
├── model/            # Внутренние модели (сущности)
├── repository/       # Слой доступа к данным (интерфейсы)
├── service/          # Бизнес-логика
│   ├── api/          # Интерфейсы сервисов
│   └── impl/         # Реализации сервисов
└── util/             # Утилитные классы (мапперы, константы)
```

- **Controller** — только принимает запрос, валидирует входные данные и вызывает сервис. Не содержит бизнес-логики.
- **Service** — содержит всю бизнес-логику: получение данных из репозитория, кэширование, маппинг.
- **Repository** — отвечает за доступ к данным (Google Sheets, БД).
- **DTO** — используются для общения с клиентом, чтобы не раскрывать внутреннюю структуру моделей.
